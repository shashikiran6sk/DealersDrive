# Android build and release operations

No release submission, cloud project creation, signing-key generation or deployment is authorized by this document. The ten PRs stay open/draft until explicit owner review. See [acceptance](production-acceptance.md) before any release.

## Local development and environments

Use repository Node 24 and pnpm 9.15.9, frozen workspace installation and the existing local Postgres/API setup. The native app is `apps/mobile`; `pnpm dev:mobile` starts Metro for a development client. Install Android Studio/SDK and JDK 21 from their official vendors on an authorized development machine. The local machine used for this checkpoint has neither SDK nor JDK, so no local native compile is claimed. For an emulator use the existing example's 10.0.2.2 API/web origins; for a physical phone use an authorized LAN development host, never production secrets or publicly exposed dev servers. Use `pnpm --filter @dealers-drive/mobile android` after SDK setup for development only.

Dynamic `app.config.ts` retains the approved static app.json artwork/permissions. Development and preview use distinct `.dev`/`.preview` application IDs. Preview requires explicit HTTPS service origins. Production additionally requires owner-approved APP_ANDROID_PACKAGE, positive APP_ANDROID_VERSION_CODE, APP_LINK_HOST matching the website and APP_RELEASE_APPROVED=true after separate authorization. The flag prevents accidental builds; it is not authorization by itself. Do not encode tokens or secret values in public origins or build metadata. No production package identity has been reserved or finalized.

`eas.json` pins CLI 24.14.0 and separates development-client APK, preview APK and production AAB profiles. Only public app-environment selectors are committed; configure the reviewed API/web origins in the chosen authorized environment. No EAS project/account/resource exists as a result of these files. Do not run EAS initialization/build/submit against a cloud account until authorized. Production configuration intentionally fails without its explicit inputs. No OTA/update channel has been enabled.

## Native validation CI

`.github/workflows/android.yml` runs only relevant mobile/contracts/config/lockfile PR changes. It uses JDK 21 and the generated Expo SDK Android project, builds arm64/x86_64 release variants with the template's debug/validation key, and uploads APK/AAB plus manifest report for seven days. Endpoints use reserved `.invalid` hosts: these artifacts cannot contact production or verify live customer flows. They are not Play-signed release artifacts. Main's general CI still verifies the existing website/API; no deployment action is added.

`check-android.py` uses the hash-pinned build-only parser in scripts/requirements.txt (install into a temporary Python target directory), forbids DTDs/entities/external access and inspects the merged release manifest (target ≥36, no debug/backup/cleartext, minimal permissions) and every packaged arm64 ELF LOAD alignment. Android build-tools zipalign separately checks 16 KB ZIP alignment. Runtime on 16 KB and normal page-size devices remains necessary. A checksum-pinned official Maestro CLI and commit-pinned emulator runner exercise guest navigation/links on an isolated Android 15/API35 x86_64 emulator; API36 image ANRs and required Android16 runtime validation are recorded separately and upload native screenshots/results; this does not verify real APIs, OTP or physical devices. Local pinned Expo prebuild and Android Hermes export are distinct evidence from a completed Gradle build. Record GitHub artifact IDs, hashes, head SHA and device evidence before acceptance.

## App Links

The app accepts a bounded allowlist of public/customer destinations and rejects arbitrary origins, privileged routes, credentials, repeated or unsupported query parameters, traversal and malformed paths. A link can open a protected screen but never authenticate, deactivate or submit an enquiry. HTTPS filters are generated only for an explicit matching APP_LINK_HOST; no arbitrary-host association is shipped.

The owner must finalize the package and obtain the **Play App Signing** SHA-256 certificate (not merely the upload certificate). Publish a reviewed `/.well-known/assetlinks.json` for the authoritative website with that package/certificate through a separately approved web/deployment change. It is intentionally not fabricated here. Verify domain association on an installed release using Android's app-link verification tools, including links opened while closed, warm and backgrounded. Uninstalled users retain the website fallback. No OAuth callback token is accepted through these links.

## Signing, versioning and submission

After all gates pass, owner-controlled signing must replace validation signing. Keep keystores/credentials.json outside Git and CI logs; both are ignored. Use Play App Signing with a restricted upload key and approved backup/recovery ownership. EAS credentials access must be separately authorized; no production key has been created or uploaded. Increase versionCode monotonically based on Console's latest accepted code; change display version intentionally and record the exact Git SHA/build profile. Verify the actual signed AAB certificate, merged manifest, supported ABIs, bundle contents, permissions and 16 KB compatibility again.

Owner approval is required before merges, production migrations/backend/web release, policy publication and Play submission. Prefer internal testing, required closed testing, then owner-approved staged rollout with pause/rollback criteria. A previous AAB cannot be republished using an old versionCode; prepare a new compatible build from a reviewed revision. Never use CI's validation-key AAB for submission.

## Incident and rollback

Stop/pause the rollout through owner Console access for authentication, consent, isolation, crash or data-loss incidents. Disable new native authentication through the existing backend feature flag only under authorized operations; avoid unnecessary disruption to the website. Preserve minimum compatible API contracts and all immutable consent evidence. F106 nullable retry fields can remain unused; F107 deactivation enforcement must remain even if its UI is rolled back. Never return to a backend that ignores deactivated customers, undo withdrawals or restore revoked sessions. Restack only through a documented compatibility assessment and authorized normal parent-into-child merges; no shared-history rewriting or automatic PR merging.

## Observability and data safety

Existing backend request IDs, Pino and Grafana cover API latency/errors and auth/enquiry/support failures. Do not log OTPs, phone numbers, tokens, headers, private messages or full URLs with query credentials. Native error recovery shows generic text, never exception contents. No new analytics/Firebase/crash SDK was added; Android Vitals requires Console/internal testing and is not yet verified. Before launch establish an owner dashboard for version/OS crash/ANR counts, startup, API p95/error rates, OTP categories/rate limits, enquiries, saved and support mutations. Alert immediately on isolation/consent violations and sustained authentication or critical mutation failures. Correlate sanitized request IDs, never customer records. A crash-free objective needs an actual denominator/sample window; no launch rate is claimed.

Data safety draft inventory: account name/verified phone and existing user identifier; saved choices; enquiry/consent/support content; request/device metadata processed by the API; optional user-triggered dealership sharing; existing processor/outbox data. Validate actual SDK/binary/network behavior, retention and the meaning of collection/sharing in Console. SecureStore holds opaque credentials; public browsing caches remain in memory and private caches clear on owner changes/logout. No location/camera/contact/storage/microphone/SMS-read/notification permission or push SDK is needed. Do not declare Data safety complete until owner/legal review, processor inventory and deletion fulfilment are approved.
