# Android acceptance matrix and execution procedure

Status: automation covers contracts/services/components; installed Android E2E, accessibility, performance and live-provider scenarios are NOT EXECUTED. This is a launch gate, not evidence that those tests passed. Each execution must record app Git SHA/version/package/signing fingerprint, API revision/legal publication, OS/device/RAM, network, operator, date, result, screenshots and sanitized request IDs.

## Required device and network matrix

Budget physical Android: 3–4 GB RAM, minimum supported OS from the generated native build, ~360 × 800 CSS-equivalent layout. Mid-range physical Android: 6–8 GB RAM, modern supported OS, ~393 × 873. Modern Android 16/API 36 emulator/device: ~412 × 915 plus 16 KB page-size environment. Include the pinned SDK's actual minimum/target rather than assuming old Expo values. CSS sizes are visual references, not hardware requirements. Test gesture and three-button navigation, keyboard resize, edge-to-edge/cutouts, 100%/130%/200% font scale and TalkBack.

Normal 4G baseline: approximately 10 Mbps/80 ms RTT; degraded: 1 Mbps/300 ms plus packet loss; fully offline; connection lost after a mutation is sent. Record actual shaping and measurements. Restore normal networking afterward. Use authorized test users/dealers/cars and local/staging services; no automatic production mutations or OTP spend.

## Reproducible device smoke entry

The optional local Maestro flows in `apps/mobile/e2e` use the installed app ID supplied as APP_ID. Install a reviewed Maestro CLI from its [official instructions](https://docs.maestro.dev/maestro-cli/how-to-install-maestro-cli); it is test tooling, not an app dependency or cloud service. After installing the preview validation APK on an authorized emulator/device, run `maestro test -e APP_ID=com.dealersdrive.customer.preview apps/mobile/e2e`. They clear only the named disposable app's local test state, exercise guest navigation/denied links and capture native images. They do not send live OTP, create an account, accept legal terms or submit mutations. No execution is claimed; verify selectors against the first real build and preserve failed artifacts rather than weakening assertions.

For full end-to-end flows use the actual local/staging Express API and PostgreSQL with dedicated test fixtures and the existing fake OTP provider in local mode. Production must retain its real provider/rate/legal gates. Do not install a test bypass in production or report fake delivery as real MSG91 verification. Live provider checks require owner-supplied test numbers and authorized spend; Google customer login is not added because the source's Google login is the dealer workflow.

## Performance collection and acceptance

Collect release-build startup traces (ten cold/warm launches per device/network after warm-up), inventory useful-content time, detail cached/uncached navigation, image first-display/cache hits, suggestion latency after 250 ms debounce, scroll frame/jank traces, PSS after 20 list/detail/gallery cycles and background restores. Proposed targets: cold usable shell p95 ≤3 s budget/≤2 s mid-range, warm ≤1 s, normal-4G inventory ≤3 s, cached detail ≤200 ms, uncached detail p95 ≤2 s, suggestions ≤1 s after debounce, 60 fps target, provisional PSS ≤250 MB/no monotonic growth. These are targets, not measured results. Record backend latency and sample size separately; do not infer native speed from mocked Jest timings or a JS export.

Before GO, execute every launch-critical installed/manual scenario on the recorded device matrix and resolve critical/high failures. Required physical-device, live-provider, deletion, legal and signing checks cannot be replaced by screenshots from a web browser or a passing unit test.
