# Legal and consent UX implementation report

## Executive summary

Consolidated the legal experience into Terms & Conditions and Privacy Policy, with one linked affirmative control for each relevant decision. Dealer contractual acceptance now occurs at successful owner Review & Submit. Authenticated customer sharing permission is scoped to a dealership and reused only for a new customer-initiated enquiry. Withdrawal, actor authority, publication review and immutable evidence remain server-enforced. Public map iframes are replaced by address and Get Directions.

All policy text remains **REVIEW_REQUIRED**, with no effective date or approved publication. Production legal enforcement/publication has not been enabled. No production records, real OTPs, emails, payments or production deployment were used. Following the user's clarification, the implementation updates existing Draft [PR #279](https://github.com/shashikiran6sk/DealersDrive/pull/279); no second PR is intended.

## Security and privacy findings

- **Unauthorized sharing/identity spoofing:** customer identity is resolved from authenticated server sessions. No caller-supplied customer/actor/phone/email establishes authority. Guests cannot use a typed contact or client cookie to reuse consent; the enquiry API requires authenticated identity.
- **Cross-dealership reuse/transfer:** receiver comes from the current available listing, with listing/vehicle ownership checked under locks. Expected recipient is compared, never used as a tenant selector. Grant queries match authenticated customer, dealership, purpose, data categories, notice version/hash, expiry and withdrawal state.
- **Consent and withdrawal races:** a customer/dealership transaction lock serializes creation/reuse/withdrawal; the existing customer/listing lock prevents duplicate open enquiries. Grant, enquiry, disclosure evidence, audit and outbox are transactionally consistent. Repeated withdrawal is deduplicated by its grant reference. Each enquiry still requires an explicit customer action.
- **Rollback/flag safety:** recorded grants continue to be checked for dealer disclosure even if new collection is disabled. Known sharing history cannot fall back to an unpermissioned new enquiry after withdrawal/expiry/scope change. A disabled API rejects supplied agreement/sharing collection payloads. The deployment rollback plan still freezes new enquiries and lead delivery before reverting enforcement.
- **Future disclosure:** grant withdrawal masks related inbox contact/message fields, suppresses dashboard details and pending notification content. Notification delivery rechecks permission before send. Already delivered or in-flight external messages cannot be recalled; dealership-held copies require separate lawful handling.
- **Representative impersonation:** assisted OTP/email cooperation provisions the actual owner account but is not a contract. Sales submission accepts an empty body only; representatives cannot supply accepting actor IDs. Final acceptance checks active authorized OWNER membership in the transaction. Approval, manual activation, reinstatement and restricted listing publication enforce applicable owner agreement.
- **Duplicate/lost evidence:** hashes and event keys are server-generated; receipt retries deduplicate. Old identifiers/content/hashes/events remain unchanged. Append-only triggers block ordinary UPDATE/DELETE/TRUNCATE; grant references and metadata uniqueness preserve history. Privileged database administrators remain an operational custody concern.
- **Version mismatch/publication:** document-specific versions/hash metadata are checked for publication; Terms acceptance and Privacy acknowledgment remain separate. Sharing and vehicle notice versions are independent. Draft source/notice versions and missing approval/effective metadata block production collection/publication.
- **Analytics:** preserved #309's provider integration while excluding private route initialization and private/custom events, stripping URL query/fragment payload fields. No consent for analytics is inferred from a sharing grant or Privacy acknowledgment. Provider request/referrer handling and lawful grounds remain release review items.

## Compatibility, risks and safe rollback

Apply the four additive migrations before matching API/web/contracts deployment; keep production flags off for this review. Existing users, dealerships and enquiries receive no fabricated acceptance or broad sharing grant. Legacy verified/active businesses use an explicit owner checkpoint before newly enforced capabilities; drafts retain contact verification, details and uploaded documents. Missing/incomplete historical sharing evidence is not inferred as a valid broad dealership permission. Source archives and receipt IDs remain available for lawful retrieval/support.

The nullable columns do not rewrite existing rows. The enquiry grant index is built concurrently; foreign key validation is separated. DDL/constraint operations still need short locks: rehearse against production-shaped data with deployment lock/statement timeouts and watch blocking transactions. Reconcile any manually applied #279 schema/history before migration; do not blindly mark migrations applied or drop evidence.

Rollback must retain a grant/withdrawal-aware API. A direct rollback to pre-consent main would ignore new withdrawal evidence. Freeze new enquiry submission and lead delivery through the existing deployment controls during an incident, preserve current masking/withdrawal/history, and restore a compatible build. Keep schemas, snapshots and all new evidence; never reverse hashes, delete grants or backfill acceptance. Review delivery logs without replaying suppressed lead jobs. Database roles, privileged retention maintenance, backups, erasure and electronic-record custody require operational approval.
